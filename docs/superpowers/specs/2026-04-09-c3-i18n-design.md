# C-3: i18n / WPML・Polylang 対応 設計仕様

**日付:** 2026-04-09
**ステータス:** Approved
**関連:** HANDOFF.md C-phase ロードマップ, C-1 WooCommerce (完了)

## スコープ

WXR から WPML/Polylang の使用を検出し、投稿に locale を付与。Next.js App Router の `[locale]` i18n routing scaffold を生成する。

**スコープ内:**
- WPML 検出 (`wpml_language` メタキー)
- Polylang 検出 (`language` タクソノミー via terms)
- 投稿への locale 付与 (WpPost.locale フィールド活用)
- 検出された locale リストの抽出
- Next.js i18n scaffold: `[locale]` dynamic segment, middleware, locale config
- CLI analyze コマンドへの統合

**スコープ外:**
- 翻訳リンク解決 (hreflang, 言語切替 UI)
- WPML `icl_translations` テーブルのパース
- Polylang `post_translations` タクソノミーの解決

## 設計判断の根拠

1. **検出 + scaffold のみ:** 翻訳リンク解決は WPML/Polylang でデータ構造が異なり複雑度が高い。scaffold で表現しにくく、移行アクセラレータとしては i18n routing の骨格を出すのが価値。
2. **`[locale]` dynamic segment:** Next.js 公式推奨パターン。C-1 の `(shop)` グループの上に挿入可能。locale 追加時にファイル複製不要。
3. **既存 terms + meta を活用:** C-1 で追加した WpPost.terms から Polylang の `domain === "language"` を取得。WPML は既存の meta から取得。wxr-parser への変更不要。
4. **C-phase 順序 (C-1→C-3→C-2):** i18n は EC と親和性が高く、C-1 WooCommerce scaffold と組み合わせた多言語 EC の基盤になる。

## アーキテクチャ

```
WXR (既存パース結果: WpPost[] with terms + meta)
  │
  ▼
analyzer/i18n-detector.ts  ← NEW
  │  投稿の meta/terms から多言語プラグインを検出
  │  - WPML: meta["wpml_language"] → locale
  │  - Polylang: terms.find(t => t.domain === "language") → locale
  │  - locale リスト抽出 + デフォルト locale 推定
  ▼
analyzer/i18n-scaffold-generator.ts  ← NEW
  │  Next.js i18n scaffold 生成
  │  - middleware.ts (locale 検出 + リダイレクト)
  │  - i18n/config.ts (locale リスト, デフォルト locale)
  │  - app/[locale]/layout.tsx
  │  - app/[locale]/page.tsx
  ▼
CLI (既存 analyze コマンドに統合)
```

## 新規ファイル

### analyzer パッケージ

| ファイル | 責務 |
|---------|------|
| `i18n-detector.ts` | WXR 投稿から WPML/Polylang を検出、locale 付与、locale リスト抽出 |

## 型定義

```typescript
interface I18nDetectionResult {
  plugin: "wpml" | "polylang" | null;
  locales: string[];
  defaultLocale: string;
  postLocaleMap: Map<number, string>;
}
```

## 検出ロジック

### WPML 検出

投稿の `meta["wpml_language"]` が文字列として存在する場合:
- plugin = "wpml"
- locale = meta 値 (e.g. "en", "ja", "fr")

### Polylang 検出

投稿の `terms` に `domain === "language"` が存在する場合:
- plugin = "polylang"
- locale = term の `slug` (e.g. "en", "ja")

### 優先順位

1. WPML を先にチェック (meta ベースで高速)
2. WPML が見つからなければ Polylang をチェック (terms ベース)
3. どちらも見つからなければ `{ plugin: null, locales: [], defaultLocale: "", postLocaleMap: new Map() }`

### デフォルト locale 推定

検出された locale の中で最も投稿数が多いものをデフォルトとする。同数の場合は先に見つかったものを採用。

### Locale バリデーション

検出された locale 値はパスセグメントとして使われるため、安全性を確保する:
- ISO 639-1 互換パターン (`/^[a-z]{2}(-[a-z]{2})?$/i`) に一致するもののみ許可
- 不正な値はスキップ (fail-safe)
- Polylang の `domain === "language"` 検出時、slug が ISO 639-1 パターンに一致しない場合は無視（他プラグインの同名タクソノミーとの競合防止）

### パス構成

`[locale]` はルート直下に配置: `app/[locale]/...`。C-1 の WooCommerce scaffold と組み合わせる場合は `app/[locale]/(shop)/...` となる（`[locale]` がルート）。

## Scaffold 生成ファイル

| パス | 内容 |
|------|------|
| `middleware.ts` | Accept-Language ヘッダー + cookie から locale を検出、パスに locale prefix がなければデフォルト locale にリダイレクト |
| `i18n/config.ts` | `locales: string[]`, `defaultLocale: string`, `type Locale` 型定義のエクスポート |
| `app/[locale]/layout.tsx` | `params.locale` を受け取り `<html lang={locale}>` に設定、locale バリデーション |
| `app/[locale]/page.tsx` | locale 付きホームページスタブ (locale 表示 + 全 locale へのリンク) |

## CLI 統合

`analyzeFromWxr` で i18n 検出を実行。WXR パース後、scaffold 生成前に `detectI18n(wxr.posts)` を呼び出す:
- 検出された場合: consola でプラグイン名と locale リストを表示
- `--output` 指定時: i18n scaffold ファイルも出力ディレクトリに書き出し
- レポートの consola.box に i18n 情報を追加
